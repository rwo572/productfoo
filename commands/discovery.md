productfoo's **discovery** command manages studies and approved unassigned-call evidence in `discovery/`. It matches completed-call metadata before access, proves study-local approval, keeps the full transcript in runtime memory only, screens a closed paraphrase envelope, reconciles findings, and stops for review.

## What the harness ships

A thin launcher only: run `foo discovery $ARGUMENTS` and relay the result. If the command was invoked bare, ask whether the user wants to plan a study or review approved unassigned customer calls first. The canonical `customer-discovery` skill owns provider calls and synthesis; the CLI owns proof, artifacts, and review transitions.

## Operating contract (printed by `foo discovery`)

These are the steps the CLI hands the agent after the command runs. They live in the command contract (`src/commandContract.ts`), so they ship with the CLI and a wording fix reaches every user on upgrade — no `foo agent setup` rerun. Editing them here alone is drift; `foo commands validate` will say so.

1. Load `foo skill customer-discovery` and follow its provider-neutral sequence. Start with `foo discovery plan --study <id>` or `--inbox`; list completed metadata only inside that scope, then use `match <study-id>` or one session at a time with `match inbox:<scope-id>` before any transcript operation.
2. Open exactly one transcript only after a unique match returns an authorized proof with target-local source approval and provider access. Keep it in runtime memory, attest the successful provider open without source content, and send only the closed sanitized evidence envelope to `apply` on stdin.
3. Stop at `needs_review`. Signals arrive tied to what they are about — Bug(s), Spec(s), Research, Idea(s), one to many: `foo discovery tie --auto` links genuine matches with agent-actor events (weak, catch-all, and no-home records stay untied); a person adds a link with `review <F-id> tie --bug|--spec <name>|--research <doc>|--idea <doc> --by <person>` (`--bug` runs the dedupe-first owner bug-log engine and ties the record to the GitHub issue; tying a dismissed record clears the dismissal) and removes one with `untie` (the GitHub issue lives on and the message says where). A person completes studies, files inbox evidence with `review <F-id> attach --by <person>` (to its one fileable tie, or `--study <id>`/`--packet <packet-name>` explicitly), undoes an attach with `detach`, edits a call's contact card with `foo discovery contact <scope-id> --name|--linkedin|--company|--title --by <person>` (`--infer` proposes candidates from local call context only — including the ones ingest already captured from provider attendee metadata, never a raw email; `--sweep` backfills inferred candidates for every scope from data already on disk), brings an archived record back with `review <F-id> restore --by <person>` (ties unchanged; the surface calls dismissal "archived"), promotes or dismisses proposals, selects duplicate sources with `review <study-id> select-source --fingerprint <sha256> --by <person>`, approves scope, and arms any budgeted schedule. Add `--within <study-id|inbox>` when a finding or proposal ID is not unique. Daily sync leaves an uncommitted `discovery/` diff only.
4. Hosted provider connections stay contract-only until productfoo's hosted service ships: a hosted target exists only after it is registered as a pending request and a person confirms that exact manifest out of band, its service grant is bounded and re-checked against the current local approval digest and revocation epoch at every access boundary, and revoking the local source (`foo source revoke`) fans out a privilege-reducing suspension to every registered target — reported as `revocation_pending` until the service acknowledges, never claimed as done. Never surface Nango or provider identifiers, credentials, or transcript content on any model-visible surface, and never claim live provider support.
5. Cross-host use is honest about where work lands: a remote host with no repository working tree may process a target only after a local runtime registered it and a person confirmed that manifest out of band, and its processed success arrives as `needs_local_apply` carrying the signed portable bundle `{envelope, processing_receipt}` for a person to hand to a local runtime — productfoo retains no copy of it — where `foo discovery apply <target-id> --evidence-stdin --json` verifies the receipt online and stops at `needs_review`. Remote paths write nothing anywhere and never report `synced`. A launcher declaring an older discovery contract is refused as `adapter_stale` with the exact repair command (`foo agent setup`), never silently invoked, and the live readiness probe is content-free, time-bounded, and runs only when explicitly requested.
